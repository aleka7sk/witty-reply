# Witty Reply privacy policy

Last updated: 1 August 2026.

Witty Reply processes only content a user deliberately sends to the Telegram bot. It cannot automatically read the user's private Telegram chats.

Operator: **Alisher Tolegenov**. Support and privacy questions: [GitHub Issues](https://github.com/aleka7sk/witty-reply/issues). Do not include private conversations, access tokens, phone numbers, or other sensitive data in a public issue.

## Data processed

The service receives Telegram account identifiers, Telegram-supplied profile fields present in the update envelope (such as name, username, and language code), and the submitted text, screenshot, image document, or voice note. Submitted content is sent to the configured AI provider to choose between the `reply` and `comment` scenarios and create suggestions. The provider receives only a fixed source-type hint such as `screenshot` or `forwarded_channel`; names, usernames, and Telegram IDs are not copied into that hint. Voice notes may also be sent to the configured speech-to-text provider.

An allowlisted Belcanto operator can ask the bot to generate a first-party Threads post. The operator first chooses a fixed publication objective and may submit up to 6,000 Unicode characters of real text material for the day. For `reach`, `replies`, `trust`, and `community`, the operator may instead explicitly continue without material; `trial` requires confirmed material and rejects the no-material action before an AI request. The material is treated as quoted untrusted evidence. The concept-planning AI request receives the objective, material kind and optional text, recent chosen post text for repetition avoidance, and the application's immutable Belcanto facts. A separate writer request receives the safe concept portfolio and produces five explicit finalists. A third blind-review request receives only the safe finalists plus the objective and evidence basis, then returns numeric editorial scores, a concise verdict, a recommendation, and an optional visual strategy. Hidden reasoning, internal scratch work, and discarded ideas are not requested or retained. Telegram then shows the five ranked finalists; replaying that stored screen or selecting one of its options does not send another request to Anthropic.

Operators should omit personal data from that material. An identifiable name or verbatim quotation should be used only with the person's permission, and information about children should be anonymized. Every material-backed preview repeats this check before the explicit publish action.

Media processing does not begin while the five text finalists are awaiting selection. After the operator chooses one, licensed-photo search sends Pexels only a fixed English object-or-space query derived from that chosen draft's validated scenario ID. Model-written queries are discarded; operator material, post text, Telegram identifiers, and user data are not sent to Pexels. A selected file is downloaded only from the allowlisted Pexels image host, normalized locally, and stored with its asset ID, source page, author, author page, and application-derived query. The operator may instead attach a real Belcanto photo; it is not sent to the AI provider. The exact text or photo-plus-text preview is sent to Meta only after the operator presses the explicit publish-confirmation button. For a photo, that button also confirms Belcanto's usage rights, appropriate context, and any required consent from identifiable people.

## Storage

- A submitted Telegram update is written to the durable inbox only as AES-256-GCM ciphertext. The encryption key is derived separately from the runtime callback secret, never stored in PostgreSQL, and the encrypted payload is scrubbed immediately after completion or final failure. The content-free terminal job record (update/user identifiers, status, attempts, and timestamps) is then eligible for the same default seven-day hourly retention cleanup. Ordinary private reply/comment source content and Telegram file URLs are not written to application domain tables or logs. The explicit Belcanto material workflow described below is the narrow durable-content exception.
- The Telegram numeric user ID, language code, consent time, and style settings are stored until profile deletion. Telegram username and first/last name may exist temporarily inside the encrypted update envelope but are not copied into profile or generation tables; the service does not fetch or store avatars.
- Source content and the immediately previous candidates are held in process memory while the short session is active so the user can request refinements, choose an ambiguous scenario, or correct the detected scenario without resending the source. They disappear after the configured inactivity TTL or a process restart; a valid action renews the inactivity window, while a stale button does not.
- Generated candidates, the resolved `reply` or `comment` scenario, a secret-keyed source digest, explicit feedback, and provider/model identifiers are normally retained for seven days by default, then removed by the hourly cleanup job. Token totals are exported only as content-free aggregate metrics, not stored per user or generation.
- A Belcanto `ThreadBrief` durably stores the operator ID, fixed objective, workflow state, material kind, optional raw text material, replay-protection update IDs, and the resulting selection/draft relationship. This allows goal/material collection and the exactly-one choice to survive a retry or process restart. It is owner-scoped and normally removed by the same default seven-day cleanup, or immediately with the operator's profile through `/delete_me`.
- The five validated finalist texts and bounded ranking metadata are retained while the operator selection is available so the same choices can be restored without another Anthropic request. They are not `ThreadDraft` previews and are excluded from the recent-text list sent to later AI requests. Once the operator chooses one, only that text enters repetition protection; the other four remain excluded. The blind editor's recommendation is material-backed when material exists, but the operator may explicitly select another fact-safe evergreen option. All five options are owner-scoped and follow the same default cleanup and `/delete_me` deletion rules.
- Belcanto Threads drafts retain only the operator's chosen finalist as the preview, plus their owned brief link, objective, selected scenario, voice, provider/model identifiers, revision, selected format, an application-derived fixed fallback photo query, publication state, Meta container/post identifiers, and permalink when returned. Evidence remains in the owner-scoped brief and content-free evidence digests in the audit. An attached or licensed photo is resized, re-encoded as JPEG to remove EXIF/GPS metadata, stored with an owner check and source provenance, and normally removed by the same default seven-day cleanup. The Meta access token, Pexels API key, and Telegram file URL are never stored in a brief, draft, finalist selection, or media row.
- The Belcanto editorial audit is a separate structured operational record. It distinguishes the blind editor's recommendation from the operator's eventual choice. Its default `full` mode contains bounded objective/scenario metadata, numeric scores, selection status, and an opaque generation ID; for no-material evergreen generations it also contains locally safe finalist texts and concise reviewer notes. Material-backed generations automatically omit every model-authored free-form field and retain secret-keyed, domain-separated HMAC-SHA-256 digests, scores, and bounded IDs only. Rejected output is always represented only by a safe code and keyed digest. A separate media-change audit records the draft revision, action, source and, in `full` mode only, the Pexels asset ID; it never logs a search query. `metadata` mode omits finalist text, free-form notes, and asset IDs; `off` emits neither event. Neither record contains the raw operator material, a raw Telegram ID, prompt, recent-post list, photo bytes, access token, or hidden model reasoning. Log-backend retention is deployment-controlled and should be limited to no more than thirty days.
- Daily usage counters are kept for quota enforcement and account operations until profile deletion; they do not contain the submitted message.
- Profile settings and style examples explicitly saved by the user are kept until reset or deletion.
- Content-free aggregated operational metrics may be retained longer.

## External processors

Telegram delivers messages to the bot. Anthropic processes AI requests when the production provider is enabled. If voice support is enabled, the voice note is first sent to the configured speech-to-text provider and the resulting transcript is then sent to the AI provider. If licensed-photo search is enabled, Pexels receives only the fixed application-derived scenario query described above. For the operator-only Belcanto workspace, Meta receives the exact approved post and, for an image post, fetches the normalized photo from a short-lived signed HTTPS URL. The URL contains no Telegram credential or user ID. Each provider processes data under its own terms and privacy policy.

## User controls

- `/privacy` shows the in-bot summary and the deployment's public policy URL.
- `/style` shows or resets personalization.
- `/threads` lets an allowlisted Belcanto operator choose a goal, submit or explicitly skip material, inspect five ranked finalists, choose exactly one, then refine that draft or attach/replace/remove a photo; only the explicit publish button sends the approved preview to Meta.
- `/delete_me` permanently deletes the user's application data after confirmation.
- A user may stop processing by withdrawing consent and deleting the profile.

## Training

Private conversations and Claude outputs are not used to train a separate generative model. Any future optional contribution to a legally reusable dataset would require a separate, explicit opt-in and is not part of v2.

## Security

Production startup rejects plaintext Telegram, Anthropic, Pexels, speech-provider, and Threads endpoints and PostgreSQL configurations that allow a non-TLS fallback. Secrets are provided through the runtime secret store, never committed to source control. Webhook requests and callbacks are authenticated, publishing is restricted to an exact Telegram-ID allowlist, and material size, media type, source host, and provenance are validated. Private Telegram source content, raw Belcanto material, raw prompts/responses, photo bytes, Telegram IDs, and access tokens are excluded from logs; only the explicitly configured Belcanto editorial audit may contain safe AI-generated finalist text.
